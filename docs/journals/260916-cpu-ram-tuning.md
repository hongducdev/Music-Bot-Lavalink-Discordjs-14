# CPU/RAM tuning — 2026-09-16

- Asked to cut CPU/RAM of the running bot. The bot and Lavalink were **not running on this machine** (no `node`/`java` for the project, port 2333 free, Lavalink's `spring.log` three days stale — the runtime still lived inside the repo then), so the JVM was measured in isolation instead of live.
- Baseline finding: `java -jar Lavalink.jar` let the JVM size its heap at 25% of physical RAM (16GB → **4.02GB**), plus a 1GB Metaspace reserve, 240MB code cache and G1's concurrent GC threads. Idle: RSS 294MB, 60 threads, 0.13% CPU (12-core scale).
- Measured five JVM configurations with a throwaway driver that opens Lavalink's WS, PATCHes a player and holds it (no Discord login needed). Winner: `-Xms64m -Xmx768m -XX:+UseSerialGC` + Metaspace/code cache/direct caps → **RSS 200MB, 46 threads, 0.01%**. G1 at the same heap floor: 244MB. ParallelGC: 429MB (rejected). `-Xms256m` cost ~50MB RSS on its own, so the heap floor stays low and `-Xmx` carries the ceiling.
- Discovery that changed the interpretation: Lavalink does **not** start the decode/encode pipeline before the voice connection exists — every `playerUpdate` in the window reported `connected=false, position=0`. The sampled CPU is therefore idle/GC overhead only; real playback CPU still needs a live measurement on the VPS.
- Chose SerialGC over G1: fewest threads, no concurrent GC work, and a small heap means the rare full GC is covered by `frameBufferDurationMs: 5000`. The latency-first alternative (`-XX:+UseG1GC -XX:MaxGCPauseMillis=100`) is documented, not hardcoded, via `JAVA_OPTS` in `.env`.
- Considered raising `playerUpdateInterval` (every `playerUpdate` makes `lavalink-client` rebuild the whole player JSON, queue included) and **rejected it after adversarial review**: `player.connected` is written only by those frames, and `play`/`radio` use it as the guard before sending voice op 4, so a 30s interval would re-send joins for up to 30s after connecting. The allocation saved is microseconds; the duplicate voice handshake is not.
- The same review caught a real ordering bug in the runtime's `start.sh` (then `lavalink/start.sh`): `LAVALINK_PORT` was read before `.env` was loaded, so the busy-port guard probed the built-in 2333 even when `.env` moved Lavalink elsewhere (and a busy 2333 made the launcher abort under systemd's `Restart=on-failure`). The port is now resolved after the env load; `start.ps1` already had the right order.
- Node side: discord.js defaults keep 200 messages per channel and sweep only `threads`; added `cacheWithLimits(MessageManager: 50)` plus a messages sweeper (interval 300s/lifetime 600s). Nothing under `src/` reads the message cache — every command edits its own returned message object, and `music-presence` depends on `guild.voiceStates.cache`, not messages. `npm start` now caps V8 with `--max-old-space-size=384`; `tsx` measured 128MB peak at boot versus 86MB for `dist`.
- Added a Linux launcher (`start.sh`) because the bot runs on a VPS; both launchers print the JVM line and take `JAVA_OPTS` from their `.env`. `application.yml` reads `${YTDLP_PATH}` so a Linux host can point at its own yt-dlp without editing a committed file.
- The user then asked to take Lavalink out of the project. The whole runtime (jar, `application.yml`, both launchers, `plugins/`, `logs/`, `yt-dlp.exe` — 118 MB, only two files of which were tracked) moved to the sibling directory `D:/MyProjects/lavalink-runtime` with its own `.env`, `.env.example`, `.gitignore` and README (run + systemd + the tuning numbers). The bot repo keeps only the four `LAVALINK_*` client keys, and both `.env` files must share `LAVALINK_PASSWORD`. `git rm` was not needed — the two tracked files are gone from the working tree, so the deletion shows up in `git status`.
- Mistake worth remembering: the split was scripted as "copy the runtime-side keys into the new `.env`, then delete them from the bot's". The `mv` of the directory failed (Windows lock), which broke the copy step, but the delete still ran — so `YT_OAUTH_REFRESH_TOKEN` and `SPOTIFY_CLIENT_SECRET` were removed from the bot `.env` without ever reaching the new file. `LAVALINK_PASSWORD` survived and was copied. Recovery: the omp session environment still carried the old `.env` values, so a helper run through `hub` (whose spawned process inherits that environment) wrote them back into the runtime `.env` — all three restored, 103/32/32 characters, verified by key only, never printed. Lesson stands: copy, verify, then delete — never in one chained step, since `sed -i` keeps no backup and `.env` is gitignored.
- Evidence: `jcmd VM.flags` shows 768MB heap + SerialGC active, real player creation returned 200, `npm run verify:radio` loaded 11/11 stations, `tsc` + 210 tests / 28 files pass. The libuv assertion on the invalid-token exit path predates the change (reproduced with `src/index.ts` stashed).
- Next: measure on the VPS during real playback; raise `-Xmx` if more than ~5 players run at once, lower it on a 1GB VPS.
